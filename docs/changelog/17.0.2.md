# Xivi 17.0.2 — 2026-08-16

Part of the [changelog](../../CHANGELOG.md); this file is one release and
does not change again. The design *reasoning* lives in
[the brief](../architecture.md).

The release the engine grew a business on. Four modules — article, order,
invoice and the contact module it already had — and everything they turned out to
need: money that adds up, documents from Word templates, numbers a customer can
quote down a phone, lifecycles, and links that cross between modules. Almost none
of it is code in a module; the modules are declarations, which was the claim being
tested.

The front end changed twice on the way, htmx arriving and leaving inside this one
release, and ended on Symfony UX Live Components with a real browser watching it.

## Added

- **An invoice module** ([XIV-19]). Names an order, copies its lines, carries a
  number, a lifecycle, totals and a VAT table, and prints from a Word template.
  An order can be invoiced in parts, and its page says what is still outstanding
  on each line. See §5.12.
- **Line items, totals and VAT on an order** ([XIV-16]). A line's total is worked
  out rather than typed, VAT is per line rather than per document, and a subtotal
  line restates the priced lines since the last one. A discount is a line with a
  negative price. See §5.9 for the rounding rules and why money is never a float.
- **Document numbers** ([XIV-15]). A field can be numbered from a sequence, so an
  order is called `ORD-2026-0001` on its page and in every link to it. One
  pattern — `ORD-{year}-{number:4}` — says the prefix, the padding and whether
  the sequence resets. See §5.10.
- **Repeating blocks in document templates** ([XIV-17]). A table row containing
  `[lines.description]` draws itself once per row of that collection, so a
  template can list what it is invoicing. A row naming a kind is drawn only for
  lines of that kind. See §5.11.
- **Documents from Word templates** ([XIV-4]). A module's records download as a
  filled-in .docx or PDF, from templates the customer writes in Word and uploads
  themselves. The placeholder list comes from their own field definitions, and
  generating one is recorded on the record's timeline. See §5.7.
- **An order module** ([XIV-18]), whose lines come in four kinds, and whose
  article lines inherit description and price from the article once and own them
  afterwards — so an order confirmed at 19.90 still says 19.90. A line that has
  drifted from its article says so, field by field. See §5.1.
- **An article module** ([XIV-11]) — a title, a description and a price — plus
  the `textarea` and `currency` field types it needed. The first module nobody
  had to change the engine for.
- **A `decimal` field type** ([XIV-22]) for things you measure rather than count,
  with the number of places a setting on the field. See §5.
- **Collection rows can come in kinds** ([XIV-20]) and **keep the order the
  customer put them in** ([XIV-21]), typed as a position rather than moved with
  buttons. See §5.1.
- **Records can have a lifecycle** ([XIV-14]), built on symfony/workflow: a
  module declares its states and the legal moves beside its fields, and the state
  lives in an ordinary field so it filters, exports and appears in history for
  free. Moving a record is its own permission. See §5.8.
- **A link may leave its own module** ([XIV-13]). A record's page lists what
  points at it from anywhere installed, and a list can filter one hop through a
  link. The reference picker is scoped to what the reader may see. See §7.6.
- **A module can say which modules it needs** ([XIV-23]), in two strengths:
  what it cannot work without, and what it works better with. Installing without
  the first is refused and names what to install first; without the second, the
  parts that depend on it are simply not offered. See §3.
- **Modules have a state** ([XIV-7]), `development` or `published`, so a module
  can exist in a build without being offered to anybody. See §6.2.
- **A tenant profile** ([XIV-12]) at `/settings/profile`: what this customer
  calls themselves, and the currency their instance works in. See §8.6.
- **A button per kind of line, instead of a blank row of every kind** ([XIV-29]).
  An order's form drew four blank rows and now draws none until a button is
  pressed — offering only the kinds this customer can actually fill in.
- **A browser-level safety net** ([XIV-31]). Three assertions in a real Chromium,
  over the one thing nothing else could see: that the front end is running at
  all. In its own container, never in the image production is built from. See
  §8.3.

## Changed

- **The record form is a Symfony UX Live Component** ([XIV-33]). Adding a row,
  removing one and saving are all actions on the component; `new` and `edit` are
  GET routes that put it on a page. See §8.3 for why this replaced htmx.
- **A refused save now answers 200 rather than 422.** A component that
  re-rendered is a successful render, so only the body says no. If anything you
  have reads these responses over HTTP, this is the release that changes what it
  sees.
- **The UI now needs JavaScript** ([XIV-28]). It used to work with scripting
  turned off and that is no longer promised — behind a policy that blocks
  scripts, the forms render and are not fully usable. Server-rendered is still
  true: every page is Twig and nothing in `assets/` builds HTML.
- **What a submitted record form means is no longer the controller's**
  ([XIV-30]). Behaviour is unchanged and no test moved; it is what made the
  change above a change of caller. See §8.3.
- **Line totals are a declaration rather than a module's own class** ([XIV-19]).
  The sums moved into the engine behind `LineTotals`, because two modules needing
  identical arithmetic is the engine's problem rather than theirs.
- **A record's history is compact** ([XIV-3]). An entry is one line with the
  changes behind a `<details>`; the record page shows the latest five and links
  to a history page that pages twenty-five at a time. See §5.2.
- **The export's content type comes from `symfony/mime`** ([XIV-5]) instead of a
  constant copied into `ModuleController`.
- **Pages are wider** — the content shell and the top bar go from 992px to
  1440px, which is what a list with a dozen columns wanted all along. It had been
  *narrowing* Bootstrap's own container rather than setting a width of its own.
- **This file is now one release per file** ([XIV-34]). Released versions live in
  [docs/changelog/](docs/changelog/) and `CHANGELOG.md` keeps only what has not
  shipped, plus an index. Entries are short, because a changelog that grows as
  fast as the work does is one nobody opens.

## Removed

- **htmx** ([XIV-33]), adopted in [XIV-28] and gone in the same Unreleased block
  it arrived in: the package, the importmap entry, the `hx-*` attributes and the
  reasoning behind them.
- **`assets/collections.js`** ([XIV-29]), and with it a button that cloned
  Symfony's prototype into a row carrying every field of every kind and no kind
  at all.

## Fixed

- **Editing a field no longer discards the options the form does not know**
  ([XIV-26]). Saving a field replaced its whole options array with the three
  settings the editor draws, so renaming a label wiped a choice field's
  `choices`, a reference's `module` and a numbered field's `sequence` — none of
  which could be typed back in, because the editor has no control for any of it.
- **A row added by the browser no longer loses what was typed into it**
  ([XIV-29]). A row arriving from a submission was built before its kind was
  legible, so it came back holding only the fields every kind shares.
- **Emptying a collection row deletes it again** ([XIV-19]). A disabled field
  keeps its value through a submit, so once rows carried derived values a cleared
  row still arrived carrying them and stopped looking blank.
